# TKD Cloud Reader 0.4.4

Захищене підключення до чинної бази ТКД. HTTPS і окремий WordPress
Application Password користувача tkd-cloud залишаються без змін.

## Операції

- Читання замовлень, оплат, залишків та пов’язаних документів.
- Зміна підтримуваних статусів і ручна оплата через штатні перевірки ТКД.
- invoice.draft: штатна чернетка рахунку.
- invoice.issue: випуск збереженого рахунку із номером і датою; збереження
  покупця, продавця, банку, позицій і сум. Окрема перевірка фактичної броні.
- reservation.extend: загальний строк 36, 48 або 72 години від початку броні.
  Випуск рахунку використовує штатну початкову бронь 24 години;
  наявна продовжена бронь не скидається.
- delivery.draft: чернетка видаткової на нерозподілені позиції рахунку.
- delivery.save: фактична кількість і надані серійні номери у чернетці;
  застосовуються штатні правила сканування та ревізія документа.
- shipment.issue: штатне проведення і підготовка відвантаження з перевірками
  оплати, фіскалізації, сканування, складу та доставки.
- PDF рахунку/проведеної видаткової через захищений GET без публічного посилання.

Проведення і підготовка Нової пошти не означають фізичну передачу перевізнику.
Непідтверджений або частковий результат позначається для звірки. Повторний
запит із тим самим UUID читає журнал, а не повторює списання чи оплату.
Не створюйте новий UUID для повторення невідомої/частково виконаної операції.

## Одночасна робота

Залишаються блокування редактора, ревізія стану, штатний mutex замовлення
та стійкий журнал UUID. Створення видаткових із кабінету і хмари має спільний
короткий mutex нумерації. Кабінет бере спочатку mutex замовлення, потім
нумерації; після перенаправлення вони звільняються у shutdown. Формат номерів
і штатний обробник кабінету не змінюються. Кеш лічильника очищається під lock.

## Встановлення

1. Оновити цей плагін завантаженням ZIP із заміною поточної версії.
2. Інструменти → Хмарний оператор ТКД: підтвердити наведені права і натиснути
   «Призначити хмарного оператора ТКД» для наявного tkd-cloud, ID 10.
3. Перевірити з хмари health, capabilities, document-snapshot і PDF.

Оновлення саме не розширює стару роль. Ключ доступу не потрібно створювати
знову. Тести синтетичні; live-перевірка нових маршрутів після встановлення
ще потрібна. Production замовлення не використовуються як вигадані тести.

Код відхиляє невідому схему/зміну штатних методів. Довільні SQL, PHP, метаполя,
прямі складські коригування та обхід штатних фінансових правил не відкриті.
Окремі складні сценарії (розділений рахунок, банківська атестація, TOV-оплата,
редагування кошика, зміна відстрочки) не входять до цих команд.

ZIP містить лише production PHP і цей README. Тести, клієнт, докази review
та build script залишаються у приватному репозиторії; секретів у ZIP немає.

## Сумісність 0.4.1 (кандидат для незалежного review)

Два pins оновлено за byte-exact source, SHA якого збігаються з live:
`Multi_Seller::sellers` і `Orders::claim_responsibility_locked`. Штатний список
продавців тепер не містить `vat`; цією версією дані продавців не змінюються.
Чотири залежності `TKD_Returning_Customer_20261114` обов’язково перевіряються
для документів, резерву й PDF. Їхні source є кандидатами: live збіг ще не
підтверджений. Невідповідність надалі блокує виконання; старі status/payment
не залежать від нових pins.

Точні native bodies у синтетичних тестах підтверджують: `REST_REQUEST`
зупиняє claim до accept, відповідальний та pending acceptance незмінні.
Окремий accept не дозволяє технічному користувачу прийняти чуже замовлення.
Немає impersonation або нових системних прав. Перевірка live після установки
має бути GET-only до узгодження всіх pins. Новий API усіх mismatch у цьому
патчі не додається: diagnostics, як раніше, повертає першу відмову.

## Сумісність відвантажень 0.4.2

За наданим source із хостингу оновлено pin `TKD_NP_Dispatch::status`
та додано приватний `status_read`. Публічний status залишається точкою
виклику: перевіряє id, виконує fresh, потім status_read. `status_for_list`
не використовується для дій. Дозволи й реалізація бізнесоперацій незмінні.
Точні старий/new native bodies дають однакові результати на синтетичних
сценаріях прав, підготовки, передачі та reconciliation; helpers замокані.
Це не live перевірка операцій: після review/установлення потрібні GET
capabilities та snapshots. Drift приватного методу блокує виконання.

Також 0.4.2 включає deployment-кандидати `Sales_Release::read_snapshot`,
`execute_unscoped`, їхні чотири self-helpers та
`Warehouse_Scanner::quantity_only_items`; чинний `serials` pin збережений.
Quantity-only стосується лише WM100UG1, цілої додатної кількості без SN;
інвертори/АКБ не звільняються від scanner-перевірок. Існуючі native правила
продавців/фіскалізації збережені, окремий cloud фінансовий маршрут не додається.
Тести exact execute з mock provider підтверджують fiscal preflight та stop
до stock при fiscal error; це не перевірка реальної фіскалізації.
Повні scanner task/dispatch/intent залишаються в revision. Нові кандидати
потребують runtime pin-збігу після установки; при drift виконання блокується.

## Payments source compatibility 0.4.3 (кандидат для review)

Оновлено лише повний file hash Payments за reviewed evidence, який збігається
з live hash. Усі 17 попередніх method pins та guard-перевірки незмінні.
Native зміни стосуються display label та окремого admin refund helper;
`reconcile_svitloe_refund` не відкривається через cloud API. Набір восьми
операцій і дев’ять прав ролі незмінні; `manage_options` не додається.
Регресія звіряє 17 pins із evidence та відмову refund-командам. Це не
повторний AST-аудит повного native файла і не live перевірка запису.
Після незалежного review/установлення потрібні GET capabilities/snapshots:
базовий Payments drift раніше не дозволив звірити NP/Release live.

## Fiscal compatibility та source diagnostics 0.4.4 (кандидат для review)

Оновлено 4 Fiscal Gate pins та додано 3 self-залежності за reviewed
`fiscal-source-review-20261117.json`. Native фінансові правила не копіюються
і не змінюються. Source із business-record constants у репозиторій не
додається. Лише context hash уже звірений live; решта нових pins потребують
перевірки після review/установлення.

`GET /wp-json/tkd-cloud/v1/source-diagnostics` перевіряє ВСІ фіксовані base
file/method pins, document method pins та точні field declarations незалежно
від fail-first guards операцій. Той самий HTTPS/Application Password/readcap
і no-store; параметри class/path/function не приймаються. Reflection та
читання source використовуються лише для метаданих/hash, native методи не
викликаються. Відповідь містить тільки class/method, тип перевірки, enum
причини й очікуваний/фактичний SHA256. Для field declaration — class та
фіксований field_index; неоднозначний/відсутній actual slice має null hash.
Ні source, ні шляхи, ні значення constants/полів не повертаються.

Ліміти: 1024 перевірки, 512 mismatch, 64 файли, 2 MiB на файл, 16 MiB
загалом, 50000 newlines на файл. Body клієнта обмежений 256 KiB. Досягнення
ліміту явно дає complete=false, truncated=true, verified=false, bound_reason.
Missing/drift не припиняють інші перевірки в межах лімітів. Inventory count
рахує перевірки: метод у base і document guards може перевірятися двічі.

Запуск із checkout: `python3 -m scripts.source_diagnostics`. Секрет береться
з чинного binding, proxy/TLS успадковуються; немає POST або retry запису.
CLI друкує лише валідовані metadata; exit 0 лише за complete verified.
Diagnostic success не послаблює execution guards і не доводить live write.
