# Правила роботи з ТКД — передавання в хмару, 17.11.2026

## Призначення та джерела
Це постійна інструкція, зібрана з явних вказівок власника в основному чаті та локальних журналів виконання. Вона не є знімком поточного складу/оплат. Найновіше конкретне доручення власника має пріоритет над старою домовленістю; фактичні суми, залишки, відповідальних, документи та стани завжди читати з робочої бази. Якщо доручення конфліктує зі штатними обмеженнями, пояснити конфлікт, а не обходити його.
Окремі старі доручення з номерами замовлень передані приватним повідомленням у хмарний чат; їх не слід масово виконувати повторно. Непідтверджене виконання позначати «потребує звірки», а не «не зроблено».
Не переносити секрети, банківські виписки, персональні дані клієнтів чи приватні реквізити в Git. Службові коди продавців звіряти з актуальним seller registry; відповідність людським іменам є в приватному передаванні.

## Робота з власником
- Спілкуватися українською, просто й коротко: результат, що змінилося, що лишилось.
- «Давай», «зроби», «можеш» у конкретному дорученні — авторизація виконати відповідну роботу. Не перепитувати вже погоджені суму, банк чи правило.
- Спершу прочитати базу/докази; запитувати лише факти, яких немає або які неоднозначні. Не вигадувати платника, номер бухгалтерського рахунку, факт надходження/повернення чи SN.
- Погоджений план/пакет/код не означає встановлення; встановлення не означає успішну перевірку; GET перевірка не означає виконану оплату/відвантаження.
- Нова задача не дає загальної авторизації на повторення історичних платежів, проведень або відправлення повідомлень третім особам.
- Власник хоче давати конкретні завдання з телефону без Mac. Не покладатися на локальні файли чи браузерні сесії Mac як на хмарний доступ.

## Джерело істини, конкурентна робота та повтори
- Працювати з чинною серверною базою, не створювати незалежну копію для запису.
- Штатні перевірки продавця, оплати, фіскалізації, сканування, залишків та маршруту доставки обов'язкові.
- Перед записом: свіже читання точного замовлення й зв'язків документів, права виконавця, editor lock, revision, штатний mutex та стійкий UUID журнал операції.
- Після таймауту або часткового результату спочатку звірити стан і журнал. Повторювати запит з тим самим UUID, не створювати новий для невідомого результату.
- Давній дозвіл перехопити редагування окремого замовлення не є постійним дозволом знімати блокування інших працівників.
- Не використовувати довільний SQL/PHP або пряме редагування метаполів для обходу фінансових/складських правил.
- Перевіряти HTTPS, точний дозволений хост, TLS, відсутність небезпечного redirect для авторизації. Не друкувати Authorization/cookies/ключі.

## Продавці, рахунки, ПДВ
- ТОВ «ТІ ГРУП» має бути доступним продавцем у погодженому сценарії рахунку.
- При виборі продавця ТІ ТОВ автоматично обираються рахунок/IBAN і самовивіз; у менеджерському UI ці поля мають бути зафіксовані.
- Для ТІ ТОВ платник і номер рахунку — дані бухгалтерії, які вносить менеджер; менеджер також вносить фактичні суму й дату та підтверджує. Не підставляти вигадані значення.
- Якщо власник назвав суму БЕЗ ПДВ, зберігати саме її як базу; ПДВ рахувати окремо за чинним податковим режимом. Не перетворювати 20% ПДВ на знижку. Узгоджену ціну не змінювати без підстав.
- Випущені документи й історичні оплати не переписувати мовчки при зміні продавця. Звірити узгодженість замовлення, рахунку, видаткової та платіжного запису.
- ТІ ТОВ-атестація, зміна продавця, зміна кошика й розділені рахунки не входять у вісім команд Cloud Reader 0.4.4; для них потрібен окремий перевірений шлях. Знати правило не означає мати API для його зміни.

## Оплати, рознесення, обіг
- Для продавця fop_eo застосовується банк/канал ЄМЕО (bank_emeo); точну прив'язку продавця перевіряти в базі.
- У ЄМЕО зберігати фактичну дату надходження, яку підтвердив менеджер/власник. Час створення запису й автор залишаються окремою незмінною історією. Ручне підтвердження не називати банківським імпортом.
- Обліковувати реальні повні та часткові оплати. Замовлення, рахунок, отримані кошти, видаткова та очікувана доплата — різні показники.
- Розносити непов'язані надходження тільки після достовірного зіставлення. Однакова сума сама по собі недостатня. Перевіряти банківський ID/джерело/дату/одержувача/призначення та відсутність дубля.
- Вказівка власника: надходження «за послуги» не відносити на продажі обладнання. Це не видалення банківської операції й не виключення її з загальної діяльності відповідного ФОП для банківського пояснення.
- Повідомлення про нерознесені оплати призначені лише власнику. У кабінеті окремо показувати самі платежі та помилки імпорту/доступу; виключення з черги має зберігати причину.
- Автоматичний зовнішній push/Telegram/email не вважати налаштованим без окремого доказу. Наявна локальна реалізація — сторінка/сповіщення в кабінеті.
- Нерознесений платіж на скасоване замовлення не є автоматичним дозволом поновити його. Для конкретного випадку власник може явно погодити поновлення.
- Робочий річний поріг продавця fop_md погоджений власником: 10 000 000 грн. Це внутрішній поріг, а не висновок про законодавчий податковий ліміт. Факт його збереження ще треба звірити.
- При відповіді «скільки чекаємо/що по ліміту» показувати окремо отримано, очікувані доплати, невизначені записи, використаний робочий поріг і залишок; використовувати свіжу дату, не старі цифри зі звіту.

## Статуси й відповідальні
- Право погоджувати оплату з відтермінуванням залишено власнику й одному погодженому керівнику (деталі приватно; локальна реалізація allowlist IDs 1 і 5, актуальну відповідність перевіряти).
- Технічному cloud користувачу не надавати це право через impersonation або manage_options.
- Відвантажене замовлення/наявність передоплати не повинні самі по собі помилково класифікувати замовлення як погоджену відстрочку. Штатно погоджена відстрочка залишку може існувати й після відвантаження.
- Для нових замовлень із сайту шукати попереднього відповідального за нормалізованим телефоном, призначати за чинною перевіреною логікою, але залишати статус «нове з сайту».
- Не переназначати весь старий масив ретроспективно. Якщо історія номера суперечлива, звіряти конкретні записи; сам факт схожого імені/замовлення не достатній.
- Ручне прийняття відповідальним окреме; хмарний читач не повинен автоматично забирати чуже замовлення.

## Бронь і склад
- Виставлення рахунку дає початкову бронь 24 години.
- Вибір 36/48/72 означає ЗАГАЛЬНИЙ строк від початку броні, незалежно від часу натискання. Не додавати до 24 або до поточного моменту. Старий UI «+12/+24/+48» замінений цим правилом.
- Не скидати вже подовжену бронь при повторній роботі з рахунком. Якщо обраний загальний строк уже сплив, не робити непомітний перерахунок «від зараз».
- У закріпленому рядку картки — статус, бронь і помітна кнопка «Оновити». Модуль броні — під статусом; продовження має бути доступне поруч.
- На складі показувати резерв під рахунком і час до звільнення без відкриття замовлення. Мета — швидко сказати клієнту, коли перевірити залишок знову.
- Таймер не повинен перевантажувати сайт; використовувати вже отриманий deadline і легкий відлік, не часті важкі запити.
- Фізичний залишок, доступний залишок, резерв зі складу, бронь поставки та виставлений рахунок не змішувати. Наявність на складі зелена, 0 червоний, поставка фіолетова.
- Підсумок «Разом у резерві цього замовлення» компактно праворуч.
- Списання — через штатну видаткову/відвантаження; повернення товару, повернення коштів і фіскальне коригування — окремі дії. Не повторювати завершену складську звірку.

## Доставка, сканування, пакування

- Фактична кількість і SN мають відповідати джерелу; не генерувати вигадані серійні номери. Разова фраза «серійних номерів немає» не скасовує перевірку SN для всіх моделей.
